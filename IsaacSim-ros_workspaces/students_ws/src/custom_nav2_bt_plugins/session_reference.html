세션 요약

움직이는 장애물은 자동 우회하지 않고, 감지 → 접근 → 대기로 처리한다

표준 Nav2 동작은 그대로 두되 (1 Hz 전역 재계획 + FollowPath), 별도의 VLM 이 /obstacle/is_movable, /obstacle/still_present 두 개의 std_msgs/Bool 을 낸다. 이 패키지의 실행 노드 rgbd_obstacle_localizer 가 RealSense depth 스트림과 카메라 내부 파라미터, TF 를 받아 장애물 위치를 map 좌표로 계산해 /movable_obstacle/pose 로 발행한다. behavior tree 는 그 좌표로 짧은 접근 경로를 만들어 정면으로 다가가 standoff_distance 만큼 앞에서 멈추고, 장애물이 사라질 때까지 그 자리를 유지한다.

Behavior Tree · custom_bt (copy).xml
  1. CaptureInitialPath — 우회 전 최초 전역 경로를 {initial_path} 로 래치
  2. IsMovableObstacleDetected — /obstacle/is_movable == true
  3. ApproachObstacleNormal — pose_topic, standoff_distance 0.4 → {approach_path}
  4. FollowPath {approach_path} → 정지점까지 주행
  5. WaitForObstacleClearance — /obstacle/still_present 이 false 될 때까지 유지

BT.CPP 버전. Humble Nav2 는 behaviortree_cpp_v3 를 쓴다. 패키지 초기 스켈레톤은 behaviortree_cpp(v4) 에 의존하도록 되어 있어 그대로 빌드하면 find_package(behaviortree_cpp REQUIRED) 에서 실패한다. 의존성과 헤더(behaviortree_cpp_v3/…), 등록 매크로(BT_REGISTER_NODES)를 모두 v3 로 맞춘다. CMakeLists.txt 는 현재 behaviortree_cpp_v3 를 참조하도록 반영되어 있다.

배경

로컬 코스트맵 1×1 과 스캔 마킹

테스트용으로 local_costmap 을 width: 1, height: 1, resolution: 0.05 로 줄이면 20×20 셀이고, rolling_window + base_link 중심이라 로봇 기준 사방 ±0.5 m 만 담는다. 2 m 떨어진 장애물은 이 창 밖이라 로컬 코스트맵에는 기록되지 않는다 — 범위 밖 마킹은 버려진다.

2 m 장애물을 "인식"하는 주체는 로컬 코스트맵이 아니라 별개의 채널이다.

  • global costmap — 맵 크기(또는 큰 rolling 창), /scan 을 obstacle_max_range 2.5 로 받아 정상 마킹.
  • RViz 의 raw 센서 표시 — LaserScan / PointCloud2 / 커스텀 localizer 의 Marker·PoseStamped 는 실제 거리에 그대로 찍힌다. RViz 의 "Grid" 는 바닥 격자일 뿐 코스트맵이 아니다.
  • 커스텀 RGB-D localizer — depth 이미지를 직접 읽어 코스트맵을 완전히 우회한다.

마킹은 사실상 무조건이다. VoxelLayer 의 mark_threshold 는 노이즈 필터가 아니라 "한 수직 컬럼에 점유 복셀이 몇 개 이상이면 2D 셀을 LETHAL 로 칠할지" 정하는 값이다. 2D LaserScan 은 컬럼당 히트가 하나뿐이라 mark_threshold 를 0 으로 둘 수밖에 없고, in-range + 높이 밴드 안이면 매 갱신 주기마다 즉시 마킹된다. 스톡 obstacle_layer/voxel_layer 에는 "N 프레임 중 M 히트" 같은 시간적 지속성 필터가 없다.

조건성은 전부 다운스트림 planner 에 있다: 마킹됨 ≠ 경로 막힘 ≠ 재계획. 장애물이 현재 경로 위 (+inflation) 에 있고 우회로가 존재해야 우회 경로가 나오며, 우회로가 없으면 planner 실패 → recovery 로 빠진다.

개념

토픽 이름은 주소일 뿐, 계약은 메시지 타입이다

토픽으로 흐르는 것은 바이트열이고, 이름은 라우팅 라벨일 뿐 해석 방법을 알려주지 않는다. ROS 2 는 .msg 를 rosidl 로 구조체 + CDR 직렬화기로 미리 컴파일하고, 직렬화는 필드 순서 기반이라 자기설명 정보가 없다. 수신측은 자기가 아는 타입의 코드로 위치 순서대로 역직렬화하므로 송신측이 정확히 그 레이아웃을 만들어야 한다.

DDS 는 토픽 이름 + 타입명 + 타입 해시(RIHS) + QoS 가 모두 호환돼야 연결한다. 타입이 다르면 깨진 데이터가 오는 게 아니라 연결 자체가 안 되고 콜백이 조용히 안 불린다. 메시지는 필드 집합이 고정된 구조체라 publish() 에는 완성된 구조체 하나를 넘긴다 — 관심 없는 필드는 안 건드려도 되지만(기본값) 와이어에는 항상 전체가 실린다.

요소누가 정하나XML 로 변경
토픽 이름cpp getInput("topic", …) → XML 포트O
메시지 타입cpp create_subscription<T> 의 TX (컴파일 타임 고정)
메시지 필드값퍼블리셔 코드매 publish 마다 전체 구조체

예: wait_for_obstacle_clearance_action.cpp 의 create_subscription<std_msgs::msg::Bool>(topic_, …) 에서 topic_ 은 XML 포트에서 오지만 타입 std_msgs/msg/Bool 은 고정이다. 이 노드에 상태를 물려주려면 반드시 그 토픽에 std_msgs/msg/Bool 을 발행해야 한다.

작업 방식

원본은 그대로 두고 사본에서 빌드·테스트한다

내일 이어서 작업하기 때문에 원본을 바꾸면 안 된다. 모든 실험은 복사본에서 한다.

  • colcon 빌드는 별도 워크스페이스 humble_ws_bttest 에서. 원본 humble_ws/{build,install,log} 는 건드리지 않는다.
  • BT 트리·파라미터는 원본이 아니라 사본에서만 편집·실행: custom_bt (copy).xml, custom_nav2_params (copy).yaml.
  • 매 빌드는 새 셸에서 source /opt/ros/humble/setup.bash 만 (원본 install 은 source 안 함).

1. 복사본 워크스페이스 동기화

# src 만 동기화, 빌드 산출물과 (copy) 파일은 제외
cd /home/ciderlab-server3/workspace/2026_industry_cowork/IsaacSim-ros_workspaces
rsync -a --delete \
  --exclude build/ --exclude install/ --exclude log/ \
  --exclude 'custom_bt (copy).xml' --exclude 'custom_nav2_params (copy).yaml' \
  humble_ws/src/ humble_ws_bttest/src/

2. 사본 설정 파일 생성 (없을 때만)

cd .../humble_ws_bttest/src
[ -f 'custom_bt (copy).xml' ]           || cp custom_bt.xml           'custom_bt (copy).xml'
[ -f 'custom_nav2_params (copy).yaml' ] || cp custom_nav2_params.yaml 'custom_nav2_params (copy).yaml'

3. 패키지 빌드

cd .../humble_ws_bttest
source /opt/ros/humble/setup.bash
colcon build --packages-select custom_nav2_bt_plugins \
  --event-handlers console_direct+ \
  --cmake-args -DCMAKE_BUILD_TYPE=Release
source install/setup.bash

4. Nav2 로딩 테스트 — 반드시 사본 경로만

P="$PWD/src/custom_nav2_params (copy).yaml"
B="$PWD/src/custom_bt (copy).xml"
ros2 launch nav2_bringup bringup_launch.py \
  use_sim_time:=false \
  params_file:="$P" \
  default_nav_to_pose_bt_xml:="$B" \
  map:=.../humble_ws/src/test_gird_map.yaml

확인 지점: bt_navigator 로그의 Loaded BT plugin: <타깃>, lifecycle active 도달. RViz 는 별도(rviz_launch.py), 실제 주행은 Isaac Sim tb3_env.usd 필요.

5. 검증 후 원본 반영

플러그인 소스 디렉터리만 rsync 로 되돌리고, (copy) 설정 파일의 변경분은 자동 반영하지 않고 검토 후 필요한 부분만 손으로 원본에 옮긴다. 롤백은 rm -rf humble_ws_bttest/{build,install,log}, 전체 폐기는 rm -rf humble_ws_bttest (원본 무영향), 소스는 git -C humble_ws/src/custom_nav2_bt_plugins checkout -- ..

git 참고. 저장소는 github.com/isaac-sim/IsaacSim-ros_workspaces 하나이고, git log 의 39개 커밋은 전부 clone 시점부터 있던 업스트림 릴리스 기록이다. custom_nav2_bt_plugins/ 는 아직 커밋된 적 없는 untracked 폴더이며, ros2 pkg create 는 git 커밋을 만들지 않는다.

작업 방식

작업 완료 후: 코드를 객체·인스턴스 단위로 설명한다

빌드·테스트가 끝나면 전체 요약이 아니라 각 구성요소별로 아래 항목을 채운다. 서술 순서는 소스 파일별(.cpp → .hpp), 각 파일 안에서 클래스 → 포트 → 멤버 → 메서드.

  • 클래스마다 — 이름, 상속한 베이스(BT::SyncActionNode / BtActionNode<T> 등), BT 노드 종류(Action·Condition·Control·Decorator), 담당 역할
  • providedPorts() 포트마다 — 이름 / 타입 / 방향 / 기본값 / 의미, 연결되는 블랙보드 키
  • 멤버 변수마다 — 타입, 초기화 시점(생성자 / onStart 등), 역할
  • 메서드마다 — tick() / onStart() / onRunning() / onHalted() 등의 호출 시점, 반환 BT::NodeStatus, 부수효과
  • ROS 인터페이스 인스턴스마다 — 토픽/서비스/액션 이름·타입·QoS·방향·상대
  • 등록부 — BT_REGISTER_NODES 의 XML ID ↔ 클래스 매핑, plugin_lib_names 타깃명

구성요소

DepthCentroidLocalizer 사용법

BT 노드도 독립 노드도 아닌 pluginlib 플러그인이다. 베이스는 custom_nav2_bt_plugins::MovableObstacleLocalizer, 등록은 movable_obstacle_localizer_plugins.xml, 라이브러리는 custom_movable_obstacle_localizers. 실행 노드 rgbd_obstacle_localizer 가 localizer_plugin 파라미터로 이 클래스를 로드한다(기본값).

알고리즘

  1. depth 이미지 중앙 ROI 를 스캔해 [min_range, max_range] 픽셀만 유지
  2. near_percentile 번째로 가까운 거리 = 튀는 최솟값을 피한 강건한 "가장 가까움"
  3. 그 값 + depth_band 이내 픽셀들의 centroid (u, v, depth)
  4. CameraInfo K 로 역투영 → optical frame (x, y, z). 살아남은 픽셀이 min_points 미만이면 ok = false

실행

ros2 launch custom_nav2_bt_plugins rgbd_obstacle_localizer.launch.py \
  depth_topic:=/depth_camera \
  camera_info_topic:=/front_camera_info \
  use_sim_time:=true

파라미터 네임스페이스. 플러그인 파라미터는 클래스 이름이 아니라 localizer_name 값 + . 로 선언된다. 기본값이면 키는 depth_localizer.max_range 같은 형태다. localizer_name 을 바꾸면 접두어도 함께 바꿔야 한다.

입출력 · 요구사항

  • 입력: depth Image, CameraInfo(K 필요), gate Bool
  • 출력: PoseStamped(target_frame=map, orientation 은 단위 — heading 은 BT 가 경로에서 계산)
  • TF: depth optical frame → map 변환 필요. 없으면 경고 후 그 프레임 스킵
  • gate: gate_topic 설정 시 Bool 이 true 이고 gate_timeout 안에 갱신될 때만 발행

교체는 같은 베이스로 export 한 다른 클래스를 만들고 localizer_plugin:=<그 클래스> 로 지정한다.

구성요소

BT 트리가 map 좌표를 실제로 쓰는지 — 확인 결과

파일/movable_obstacle/pose 사용내용
custom_bt.xml (원본)아니오스톡 Nav2 트리. movable-obstacle 노드 없음
custom_bt (copy).xml (사본)예ApproachObstacleNormal 이 pose 를 입력받아 접근 경로 생성
 
<ApproachObstacleNormal path="{initial_path}"
                        pose_topic="/movable_obstacle/pose"   <!-- ROI→역투영→TF(map) 결과 -->
                        standoff_distance="0.4"
                        on_path_tolerance="0.35"
                        global_frame="map"
                        approach_path="{approach_path}"
                        approach_goal="{approach_goal}"/>
<FollowPath path="{approach_path}" controller_id="FollowPath"/>

즉 rgbd_obstacle_localizer 가 낸 map 좌표를 받아 {approach_path} / {approach_goal} 를 만들고, 바로 다음 FollowPath 가 로봇을 그 경로로 이동시킨다. 이동 후 WaitForObstacleClearance(/obstacle/still_present)가 false 될 때까지 정지 유지.

단, 조건부이고 좌표에 딱 붙지는 않는다

  • 장애물이 {initial_path} 위(on_path_tolerance 0.35 m)에 있을 때만 접근. 아니면 ApproachObstacleNormal 이 FAIL → 하단 FollowPath {path} 로 일반 planner 가 우회.
  • 좌표 지점이 아니라 standoff_distance 0.4 m 앞에서 정면 정렬해 멈춤.
  • IsMovableObstacleDetected(/obstacle/is_movable == true)가 먼저 통과해야 이 브랜치가 실행됨.
